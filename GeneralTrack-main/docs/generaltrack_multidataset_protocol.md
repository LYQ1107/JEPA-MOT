# GeneralTrack Multi-Dataset Protocol for DAMOT / DARTH

## Original GeneralTrack Flow

GeneralTrack is primarily written around BDD100K MOT plus GHOST detections. The README asks users to prepare BDD100K MOT images and labels under `datasets/bdd100k`, download `detections_GHOST/bdd100k`, and run `tools/convert_bdd100k_to_coco.py` before tracking.

`tools/convert_bdd100k_to_coco.py` reads `datasets/detections_GHOST/bdd100k/<split>/<seq>/det/yolox_dets.txt`, converts each detection from `x,y,w,h,score,cls` into `x1,y1,x2,y2,score,cls`, and stores the resulting array inside each COCO-like image record as the `detection` field. The output annotation has `images`, `annotations`, `videos`, and `categories`, but the converted BDD100K validation file contains no GT annotations for tracking.

`tools/track.py` does not run detector inference in the released evaluation path. The detector checkpoint loading and model CUDA/eval setup are commented out, then `model = None` is passed to `MOTEvaluator.evaluate_bdd100k`. Tracking uses detections already packaged into the dataset JSON.

`yolox/data/datasets/mot_bdd.py` loads a COCO-like annotation file and, for each image, returns the raw image plus `coco.imgs[id]["detection"]`. `yolox/evaluators/mot_evaluator.py` passes these detections to `BYTETracker`. The expected detection shape is `[x1, y1, x2, y2, score, class]`.

`tools/txt2json_trackeval.py` converts GeneralTrack result txt files into BDD100K TrackEval JSON. The txt writer in `mot_evaluator.py` uses BDD-style MOT rows:

```text
frame,id,x,y,w,h,score,class,low,-1,-1
```

TrackEval BDD evaluation then expects per-video JSON files in its BDD100K tracker layout. For DAMOT / DARTH datasets we instead add a COCO-MOT to TrackEval-compatible in-memory evaluation path.

## Baseline Positioning

In our experiments, GeneralTrack is not a source-free adaptation method and not a continual adaptation method. It is used as a no-adaptation / source-only / generalizable MOT tracker baseline.

GeneralTrack does not perform clear-to-overcast-to-rainy-to-night sequential adaptation. It does not train on target-domain labels and it does not update the detector or tracker on target domains. It directly tests every target domain using detections generated by the same source detector.

Our method is sequential source-free multi-target adaptation. GeneralTrack answers a different question: whether a strong generalizable tracker naturally transfers across target domains without adaptation. It is not intended to measure forgetting or continual adaptation behavior.

Because GeneralTrack does not sequentially adapt, BWT is not computed for GeneralTrack. BWT is only meaningful for continual adaptation methods such as DARTH-seq, Ours, Simple-SFOD-seq, DRU-seq, AMROD-seq, and similar sequential methods.

## Detection Fairness

For a fair multi-dataset comparison, the main GeneralTrack baseline must use detections produced by the same source detector used in the source-only protocol. It must not use target-trained detectors and must not use a different external detector per dataset.

GHOST detections can be used only as an external detection reference, for example `det_source=external_GHOST`. They should not be mixed into the main fair source-detector baseline.

Ground-truth boxes are forbidden as detections in the main experiment. GT detections are allowed only for a separate oracle upper bound, must be marked as `det_source=oracle_gt`, and must not enter the main fair comparison table.

If detections are missing for any dataset/domain, source-detector detections must be generated first. The provided input inspection and run scripts report the missing path and stop for that domain instead of silently falling back to GT boxes or skipping the domain.

## Added DAMOT / DARTH Flow

The added protocol supports COCO-format MOT annotations with `images`, `annotations`, `videos`, and `categories`. Track identity fields are normalized from `track_id`, `instance_id`, or `mot_instance_id`. Frame IDs are made one-based for GeneralTrack runtime while the original values are retained as `source_frame_id`.

The conversion script packages detector outputs into GeneralTrack's existing image-level `detection` field. Supported detection inputs are:

- COCO-format detection JSON with `image_id`, `bbox`, `score`, and `category_id`.
- COCO-like JSON containing `annotations` or `detections`.
- Prepared JSON whose image records already contain `detection`.
- MOT-style txt files under a detection directory, either one file per video or a single txt file.

The tracking script reuses `BYTETracker` through `MOTEvaluator.evaluate_bdd100k`, but uses a prepared dataset directory rather than hard-coded BDD100K paths. It does not train a model, run detector inference, perform source-free adaptation, or update detector weights.

The evaluation script evaluates GeneralTrack result txt files against the target-domain COCO-MOT GT and writes per-domain metrics plus a unified summary CSV:

```text
outputs/generaltrack/generaltrack_multidataset_summary.csv
```
